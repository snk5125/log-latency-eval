Why these choices — and what they cost

The through-line is one principle: spend each scarce resource — latency, durability, storage cost, or operational burden — only where it's justified. That is what tiering is for.

A

Bucket topology

What defines a bucket boundary, and what stays a prefix.

Split buckets by governance posture, not by source

The things that actually differ between these data sets — Object Lock, replication, KMS key, default retention, access boundary — are all bucket-level features, and source drives none of them. Partition by how the data must be treated, not by what it is.

Trade-off

Sources co-mingle inside a bucket (cross-source queries; one KMS key and access boundary per bucket), and the policy grows when multiple writers share it. Finer distinctions fall to prefixes.

Tier is a prefix in the ops bucket, not a bucket per tier

Tiers 1/2/3 differ only in lifecycle, storage class, and retention — all prefix-scopable. That avoids bucket sprawl while keeping the differentiated treatment.

Trade-off

All operational tiers inherit the same bucket-level settings; promoting a tier later (its own KMS key, say) means a migration. Cross-tier queries fragment across prefixes.

CloudTrail / Config write natively, bypassing the pipeline

Native delivery is more reliable (compliance delivery doesn't hinge on your pipeline being up), preserves the pristine raw record, and auto-partitions by service.

Trade-off

Heterogeneous writers mean a bigger bucket policy (AWS service principals plus your role) and AWS-imposed key layouts that won't match your agent partitioning. If you want them in silver, the pipeline must read the bucket — an added input.

B

Delivery & resiliency

How data gets in, and where the HA burden lands.

Bulk tiers via S3 landing

The core goal: offload durability and buffering to S3 so the ingest / aggregation tier can be non-HA — no SLA, no on-call. S3 absorbs producer bursts and consumer downtime, and the aggregator drains when it's up.

Trade-off

Roughly seconds of added latency (flush-dominated), plus more object and request management. Fine wherever seconds don't matter.

Tier-0 via direct stream + durable tee

Resolves the latency-vs-durability tension for the critical slice: streaming delivers sub-second for alerting and detection, while the tee drops a durable, immutable copy for compliance and replay — so the record is safe even if the fast path isn't.

Trade-off

Data is written twice (cheap, because tier-0 is low-volume) and a fan-out to configure. The streaming path still has to exist, though it's no longer the system-of-record so it needn't be fully HA.

Tier assigned at the host for agent logs

Lets you route both the delivery path and the destination at emit time — critical to the stream, bulk to the landing bucket.

Trade-off

Only works when tier is knowable from source or path. Content-derived tiering can't happen at the host — it moves to the silver layer — and classification policy now lives in host config to maintain and deploy.

C

Governance & immutability

The one bucket-level lever that forces the split.

Object Lock (WORM) on the compliance bucket only

Tamper-proof audit and critical evidence, often regulatory. It's a bucket-level feature — which is precisely why the immutable data gets its own bucket.

Trade-off

It's bucket-wide (no per-prefix locking); default retention is bucket-level, so mixed retentions need per-object overrides; you can't delete early even when you'd want to; and you can't compact or rewrite objects after write, so right-sizing has to happen upstream.

D

Lifecycle & cost

How data cools, how long it lives, and what actually drives the bill.

Standard → Glacier Instant → Deep Archive; skip IA

Recent data stays hot for investigations, then cools cheaply for the long compliance tail. Glacier Instant keeps millisecond retrieval for the mid window; Deep Archive is cheapest for the cold tail. Standard-IA rarely earns its place for write-once, rarely-read data.

Trade-off

Deep-Archive reads need a restore (hours), so deep audits aren't instant; you pay per-object transition fees and minimum-duration charges; and small objects archive poorly (128 KB / ~40 KB minimums) — which the low-volume tier-0 partly fights.

Retention differentiated by tier (30mo / 12mo / 90d / 14d)

Storage × retention is the dominant cost, so short retention on high-volume, noisy tiers is the single biggest lever — keep only the valuable data long.

Trade-off

Aggressive expiry means no replay past the window and demands confident classification: a mis-tiered critical log could expire in 14 days. The numbers are policy calls, not derived.

Request-rate via object size and key design, not more buckets

A single bucket auto-partitions to very high rates, per-account bucketing already shards, and bigger objects cut request rate for the same bytes. Buckets are for isolation, not throughput.

Trade-off

Bigger objects raise latency (bigger flush) — the latency–rate–cost knob — and analytics-friendly date prefixes can hotspot under bursts, so you may need a shard element early in the key that fights clean date partitioning.

The meta-trade-off

Nearly every choice above spends one of four things — latency, durability, cost, or operational burden — to buy another. Tiering exists so you make that trade per class of data: streaming, immutability, and long retention on the small critical slice; cheap, non-HA, short-lived handling on the bulk. The risk that ties it together is classification confidence — the whole scheme only holds if data lands in the right tier, since that one decision sets its latency, durability, retention, and cost all at once.

Retention windows and storage-class thresholds are illustrative — set them to your compliance mandate and latency SLAs. Storage-class prices and minimums referenced are AWS list-price approximations; verify against current pricing for your region.
